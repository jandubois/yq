## Executive Summary

This change replaces the recursive `AliasNode` case in `traverse()` with an iterative loop that detects alias cycles via a visited set, preventing a stack overflow from circular aliases. The fix is correct for `traverse()`, but a sibling function `traverseArrayIndices()` in the same file contains an identical recursive alias pattern that remains vulnerable — reachable through `.[]`, `.[0]`, and every operator built on `splat()`.

Fix: extract a shared helper that both functions call, eliminating the duplication:

```diff
+func resolveAliasChain(node *CandidateNode) (*CandidateNode, error) {
+	if node.Kind != AliasNode {
+		return node, nil
+	}
+	visited := map[*CandidateNode]bool{}
+	for node.Kind == AliasNode {
+		if visited[node] {
```

Use `resolveAliasChain` at the top of both `traverse()` and `traverseArrayIndices()`, and remove the `case AliasNode` branch from `traverseArrayIndices`.

## Design Observations

**Strengths**

- Replacing recursion with an iterative loop + visited set is the right approach. It is simple, correct, and bounded. The cycle detection terminates after at most N iterations for an N-node alias chain, with O(N) memory for the visited set — both optimal for this problem.
- Placing the alias resolution at the top of `traverse()`, before the kind-based switch, is a clean separation of concerns: resolve aliases first, then dispatch on the resolved kind. This is clearer than mixing alias handling into the switch.

**Concerns**

- *(in-scope)* The alias-cycle vulnerability exists in two parallel functions (`traverse` and `traverseArrayIndices`) in the same file. Fixing one without the other leaves a known crash path open. Consider extracting a shared `resolveAlias(node *CandidateNode) (*CandidateNode, error)` helper that both functions call, so the cycle detection logic lives in exactly one place.
